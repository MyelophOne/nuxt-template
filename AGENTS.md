# @myelophone/nuxt-template — website development

This repository owns website generation, design and application delivery through @myelophone/nuxt. These rules and the local design guides travel with the template. Preserve user work.

## 1. Inspect before implementing

- Read `git status`, app config/package.json and the **installed version's** README/source. Before implementation explicitly read the resolved installed package's `AGENTS.md` for technical contracts and relevant README/source; dependency instructions are not inherited automatically. A sibling checkout is not evidence of the installed API.
- Source, public types and generated registrations establish the API; README examples can lag. Verify props/events/slots, exports/names, attribute forwarding and SSR before use. Never invent an API or assume another version supports these examples.
- Verify contracts in SSR HTML and the browser: `as` produces the requested tag, form attributes reach the real input, nested markup inherits type. Declarations alone do not prove behavior.
- Search narrowly with `rg`/`rg --files`; inspect relevant README, pages, assets, locales and tokens.
- Map needs to existing APIs before coding. State the direction; use the design brief for missing brand/palette, audience, scope, assets or contacts. Omit known answers, continue independent work; never invent facts.

## 2. Non-negotiable reuse rules

- **Do not recreate, rewrite, copy, vendor, shadow or bypass an existing component or subsystem.** Renaming a copy, hiding it in a page, or wrapping it with duplicated behavior is still duplication. No parallel button/input/modal/grid/i18n/theme/consent/search/reveal implementation.
- Use this order: existing API → supported props/slots/classes/CSS variables → page-specific composition of existing components. Compositions arrange content and delegate behavior; never duplicate primitives or add empty pass-through wrappers.
- Use native semantics for prose/lists/figures and missing abstractions, never to replace existing UI or page grids.
- Prove a missing primitive/extension with searched paths and its contract. Report the exact limitation; no silent substitute, DOM surgery or stacked CSS overrides. Consumers obtain direction for a package change/upgrade while continuing unaffected work.
- Package development belongs in its source repository under its own AGENTS.md, only within the authorized scope. Never implement a package change by editing this application's dependency installation or shadowing its component.
- For a framework defect found in browser review, identify the owner and smallest upstream fix. Once authorized, fix the layer, remove temporary application compensation and record prevention here. Do not turn the failure into a permanent site workaround; distinguish site styling from framework repairs.
- Never edit dependency installations, `.nuxt/`, `.output/`, generated declarations, caches or lockfiles by hand. Do not disable SSR, strict checks, CSP, consent, tree shaking or package optimizations to make a page work. Diagnose the owning issue.
- No extra UI/CSS/animation/icon/HTTP/state stack duplicating installed capabilities. New dependencies need a proven gap and compatibility/bundle assessment.

## 3. Auto-imports are mandatory

- **No manual runtime imports where auto-imports are available in that context.** This includes Vue APIs (`ref`, `computed`, hooks), Nuxt APIs, registered layer composables, utilities, stores, constants and components. Do not import these from `vue`, `#app`, `#imports`, `#components` or their source paths just for explicitness.
- Use registered template names, including directory prefixes; use Nuxt’s Lazy prefix for suitable deferred components.
- If resolution fails, inspect `.nuxt/imports.d.ts`, `.nuxt/components.d.ts`, Nuxt/module import settings and scan directories; regenerate with the project's prepare command. Fix a project registration/export or name collision instead of adding an import as a workaround. Do not disable `imports.scan`, auto-imports or layer scanning.
- An import is allowed only when unavailable through auto-import in that execution context: external non-registered APIs, assets/styles, build modules, standalone scripts/tests, or types absent from generated type declarations. Use `import type` for those types. App auto-imports do not imply availability in Nitro, workers, config files or tests.
- For name collisions such as `useStorage`, verify generated registrations and use the intended layer contract; never silently swap providers.

## 4. Package map: reuse these first

Package source paths in these instructions are relative to the resolved **installed layer root**, not this application. Verify the actual contract.

See [the API map](docs/creative-direction/PACKAGE-API.md) when mapping page needs to the installed layer; verify its actual version.

- The inherited `app/app.vue` owns the skip link, route announcer, `<main id="main">`, initialization and global UI (consent, preloaders, search, commands, toasts, scroll-to-top). Inspect it before composing layouts. Do not nest another main, duplicate globals or replace the app shell just to add site chrome.
- `UiButton` does not infer its root element from `to`/`href`: inspect and set its supported `as` when needed. Use `UiLangLink` for locale-aware paths. Never nest a button inside a link or blindly pass undocumented `ui`, `as` or size props.
- Use `UiIcon` for SVG icons: its mask uses `currentColor`; style through text color/CSS, not an invented color prop. `UiIcon8` currently loads PNG. No Unicode/emoji substitutes or decorative arrows everywhere; choose meaningful icons, coherent style and accessible names. Verify CSP/network loading.
- Public email uses `SafeEmail` or a verified package equivalent; no raw mailto/custom obfuscation. Check destination and no-JS limits.

## 5. Page grids must use Grid components

- **Use `GridStack`, `GridContainer`, `GridRow` and `GridCol` for page sections, content widths and responsive column layouts.** Do not replace them with a custom container system, raw page-level flex/grid wrappers or a copied 12-column grid. Use only the wrappers a composition actually needs.
- `GridStack as="section"` provides a semantic full-width section; `GridContainer` constrains content; `GridRow` contains sibling `GridCol`s. `GridContainer` renders a div: do not invent its `as` prop. Avoid redundant nested containers and padding.
- Check actual `header`/`section`/`article`/`footer` output when using `as`; never add a parallel semantic-wrapper hierarchy to conceal a broken component. In layer code, a dynamic tag uses Vue `<component :is="as">`; `:is` on a literal `<div>` does not implement this contract.
- Read `app/constants/layout.ts` for actual widths/breakpoints. In the current API `span` controls desktop columns; mobile is full width unless `smSpan` is set. This differs from Tailwind's upward `sm:` convention. Verify `mdSpan`/ordering when needed.
- For a 12-column row, avoid adding horizontal `gap` on top of columns totaling 12: it can force wrapping. Use supported gutters, e.g. row `gap-y-8 md:-mx-4` with column `md:px-4`, and verify the result. Handle overflow at its source.
- Tailwind and scoped CSS may arrange **internal component content** and provide spacing, typography and decoration. They must not become a parallel page grid. Prefer normal flow; do not absolutely position the page to resemble a screenshot.
- Use verified Grid background/media props (`bgColor`, `bgImage`, `bgImageSm`, `bgGradient`, video/poster) and check consent. Background Grid roots position direct children as content planes: use their media API, not an absolute direct-child background fighting those styles. Inspect actual responsive image URLs/intrinsic dimensions; a loaded image may still be a tiny upscaled variant.
- **Use desktop sticky compositions by default when unequal column heights benefit from retained context**: keep a short heading, summary or navigation beside longer services, steps, article content or FAQ, bounded by its own section. Prefer `ViewStickyHeadingContent` (`sticky`, `stickyFrom="lg"`, `stickyOffset`, heading slots); use `UiStickyWrapper` for other supported content. Keep the existing Grid composition. No extra sticky library, scroll listener, fixed-position imitation or copied component.
- Include header clearance; disable pinning on narrow/short screens or when content cannot fit. Verify section bounds, stretch and ancestor overflow/transform, including reveal/background layers. `UiStickyWrapper` also caps inner height when inactive. Test long translations, zoom, keyboard access and release at section end; no overflow hiding, nested scroll traps or internal overrides to conceal defects.

## 6. Design quality is part of functionality

- For an explicitly named style, use [style presets](docs/creative-direction/presets/INDEX.md), then load only the selected file. A preset tunes the page profile; it never overrides brand, system-font defaults, package APIs, accessibility, performance or SSR. Generic requests for a modern/premium site do not activate the entire preset library.

Apply this full process for new sites, new page templates and redesigns; for a small fix, preserve the established style and check the affected area. Backend-only work skips art direction.

- **Read [the design guide](docs/creative-direction/DESIGN.md)** for new sites/templates/redesigns. Follow brief → composition/API map → wide/narrow slice → complete site → visual/task refinement → dual-mode checks. Keep site DESIGN.md concise.
- For layout/UX work consult [the router](docs/creative-direction/layouts/INDEX.md), then only matched page/element/workflow files. Never preload the library. Explicit layouts win. Choose entry/density for the task, not an obligatory hero, terminal or dashboard. Large hero images span the viewport unless directed otherwise. Show actual subject/evidence at useful scale, not crude media substitutes.
- For a new visual identity use [art direction](docs/creative-direction/layouts/workflows/ART-DIRECTION.md): subject, type, composition and motif must tell one story on desktop/mobile and without motion. Avoid name/color-swapped slogan/three-card/logo/CTA sequences. Content minima mean useful depth, not padding. Fix composition before decoration; step markers and emphasis need actual meaning.
- **Demonstrations must explain the real offer.** Keep input/output, labels and selected state coherent; crop to readable detail. Comparisons need verified values/units/context. Copy/download/search/filter controls must work when included; use actual data and existing primitives, not fake proof or dashboard chrome. See the guide's task and proof contracts.
- Use actual semantic tokens for surfaces, text roles, accent, border/focus/status, spacing/radii/shadows/type. Map inherited `--ui-bg`, `--ui-text`, `--ui-border`, `--loader-fill-color`; verify rendered themes. Quiet supporting text needs contrast, not group opacity. Respect `data-theme="light|dark"` through the settings store.
- **Always include a visible light/dark switch** in shared mobile/desktop chrome unless the user requires one theme. Use the installed `UiThemeToggle` (optional localized `label`, normal button attributes), which composes UiButton/UiIcon and delegates state to useSettingsStore. Do not recreate the switch, state, persistence or provider. Verify one visible icon, accessible name/focus, keyboard/touch, both themes, reload and cross-tab sync; preserve SSR agreement. If absent in an older dependency, report the API gap/upgrade path instead of copying it.
- **Use web-safe system fonts unless explicitly specified by the user/established brand**, preferably the inherited stack: `system-ui`, `-apple-system`, `BlinkMacSystemFont`, `'Segoe UI'`, Arial, `sans-serif`; Georgia/`'Times New Roman'` with `serif` can provide a deliberate role. No remote font CSS/packages for novelty. Explicit custom fonts use the existing pipeline and safe fallbacks. Verify glyphs, computed/inherited type, fluid bounds, leading and actual language wraps; no `!important` repairs.
- Inline text must inherit surrounding type size/leading unless deliberately styled. Check nested heading text, wordmarks and button labels. Fix package-wide inline resets upstream; never scatter page compensations. Preserve native inheritance and explicit type utilities.
- **Buttons must pass the guide's geometry review**: coherent heights, padding, label/icon alignment and readable type at actual size. No automatic full-width slabs, oversized rounding or bold labels. Visual failure blocks delivery even when contrast/build checks pass.
- **Choose a coherent, replaceable palette**, assign semantic roles and verify contrast in both themes. User colors override examples. Keep HEX values in one application palette; components consume roles. Use clear, intentional surfaces, purposeful shadows and harmonious Grid/view gradients unless flat fills are requested. **No default milky/cream/beige-gray page grounds, white haze/veils, foggy pastel fills or blur/glow blobs.** Pale swatches are not automatic backgrounds. Keep media sharp; edge blur stays local. User-requested cream/pastel branding is an explicit exception, not a default. Starting sets from Color Hunt **Popular / Month, observed 2026-10-21** (not all-time rankings). Derive readable text/surface/state tones; record adaptations:

  | Direction         | Concrete source colors                  | Suggested use                                           |
  | ----------------- | --------------------------------------- | ------------------------------------------------------- |
  | Smoky blue / milk | `#AEC4D4` `#F5EFE1` `#E5D3AF` `#790D16` | Blue accent, milk ink on dark, sand/wine details        |
  | Sage / rose       | `#84A282` `#B8CFB3` `#FEFAF3` `#F6E2E9` | Sage accents, cream/rose details; deliberate ground     |
  | Botanical         | `#D1EDD3` `#ACC5A6` `#89A482` `#5C7057` | Related green surfaces; add sufficiently dark/light ink |
  | Marine            | `#FFEFC4` `#97D7FF` `#4D8DBA` `#086288` | Blue emphasis, light blue/cream details                 |
  | Editorial earth   | `#4C4541` `#F2C46A` `#AEAC78` `#FCF0DA` | Brown ink, olive/gold accents, cream detail             |

- Use existing `v-reveal` on suitable below-fold groups; keep hero/LCP immediate. No second reveal engine, long queues or scroll hijacking. **No hero slider by default**; a necessary one uses a minimal existing API and fast first frame. **3D animation needs explicit user request.** Consider editorial card offsets/scale within Grid; preserve mobile/DOM order. For local edge fades/blur or scroll letter color, read [motion guidance](docs/creative-direction/MOTION.md).
- **Design visible image hover feedback** for project/product/card previews: a bounded crop scale, restrained tone/overlay change or real caption response through existing APIs and owned CSS. No routine blur, fake pointer/action or new dependency. Fine-pointer motion only; linked previews need keyboard feedback, touch keeps content/actions visible, reduced motion keeps static feedback. Verify actual hover/focus before/after, sharpness and no layout shift; static decorative images may stay still. Preserve no-JS visibility and package device/network fallbacks.
- Use relevant finished assets and purposeful crops. No fabricated logos, clients, testimonials, awards, metrics, misrepresented product screenshots or business claims; no placeholder content, random stock or broken media in a finished site. Ask for essential missing facts/assets.
- Every action needs a useful outcome and prompt, truthful feedback. Complete pending/empty/error/success/disabled states; transitions stay interruptible. Never fake auth, progress, copy/download or submission success, guess assets/contacts, or use `href="#"`. Test the full journey, rapid input and recovery.

## 7. Page depth and search-facing content

For **new public marketing/content pages**, use these project defaults unless the user specifies otherwise. A block means a distinct useful section in the main content, not a wrapper, paragraph, header/footer, cookie banner, decorative strip or duplicated mobile variant. SEO sections are a subset of the total, not extra sections appended after the page.

| Page type                     | Minimum substantive sections                                                 | Minimum search-facing text sections | Original visible prose target                |
| ----------------------------- | ---------------------------------------------------------------------------- | ----------------------------------- | -------------------------------------------- |
| Homepage / corporate overview | 7                                                                            | 3                                   | 500–800 words                                |
| Campaign / conversion landing | 6                                                                            | 3                                   | 400–700 words                                |
| Service / solution detail     | 7                                                                            | 3                                   | 600–1,000 words                              |
| Product detail                | 6                                                                            | 3                                   | 350–650 words, plus actual specifications    |
| Catalogue / category          | 4, including the real listing                                                | 2                                   | 250–450 words, excluding repeated item cards |
| Article / guide               | 4 meaningful body subsections, plus introduction and conclusion where useful | The article itself                  | 600–1,200 words, adjusted to the question    |

- Word ranges are editorial targets, **not ranking requirements or guarantees**. Count whitespace-separated words in original visible prose, excluding chrome, metadata, repeated cards and duplicate locales. Write naturally; never pad.
- A homepage may cover proposition, offering, differentiation, process, application/example, decision support and next action. Adapt the composition to the product; never fabricate proof, clients or reviews.
- Three search-facing sections cover distinct intent: **offer/audience; practical details/process/specifications; decision support** (limitations, selection advice or real questions). Integrate descriptive h2/h3 sections into the composition. FAQ is optional; mark up only visible actual FAQs.
- Each search-facing section needs two developed paragraphs or equivalent useful prose/lists/facts, roughly 80–180 words as appropriate. Integrate text where it helps; no generic SEO footer dump.
- Keep search-facing text in SSR HTML, readable without modals/animation. No hidden keywords, name-swapped location pages or repeated paragraphs. Align title, description, h1 and links with intent; localize meaningfully.
- Apps, dashboards, account/auth, checkout, utilities, errors and legal documents follow their actual structure without forced marketing blocks. Small edits preserve depth; explicit short briefs override defaults.
- If truthful content cannot support the minimum, request missing inputs; never pad or invent. Check counts, coverage, prose and reading quality together with design.

## 8. Nuxt 4 engineering baseline

- Use Vue SFCs with `<script setup lang="ts">`, Composition API, typed props/emits and stable item keys. Follow the installed Nuxt version and existing formatting. Do not introduce Nuxt 2 patterns, Vuex, a custom router or duplicate route registration.
- Use Nuxt 4 `app/` directories for client application code. Honor this layer's configured `serverDir: 'app/server'`; do not assume a root `server/` is the only active server directory. Keep Node/build code out of client bundles. Use `.client`/`.server` suffixes only for real execution boundaries.
- Keep routes thin, chrome in layouts, domain compositions in components. Do not globalize component-local behavior through plugins/watchers.
- **SSR data:** use `useFetch` for suitable endpoints or `useAsyncData` around the existing `useApi`/other service call. Instantiate context-dependent clients in setup before the async handler. Do not perform bare initial `$fetch`/API calls in universal setup and repeat them on hydration. Use event-driven calls for mutations.
- Async-data keys must reflect the resource and changing route/query/locale dimensions. Keep handlers free of side effects and return defined data; keep shared-key options consistent. Fetch independent data concurrently; use `pick`/`transform` to limit payloads. In Nuxt 4 async data is shallow by default: replace values or explicitly justify deep reactivity instead of relying on nested mutation.
- Use `callOnce` for appropriate store initialization side effects. `lazy` controls navigation blocking, not a blanket exemption from SSR work; use `server: false` only for intentionally browser-only data, with a real pending state. Preserve meaningful SSR content, especially with streaming enabled.
- **State:** use local refs for local UI, `useState` for small serializable shared SSR state, and existing Pinia stores for their domains. No mutable module-scope user state or store instances shared across requests. Never serialize credentials, functions or arbitrary class instances into the public payload. Browser persistence is not server authority.
- **Hydration:** first server/client render must agree. No viewport, localStorage, random/time-dependent markup or browser DOM access during SSR. Prefer responsive CSS and package APIs; use `useId` for stable IDs when appropriate. Call context-dependent composables in supported Nuxt contexts, not module scope or arbitrary delayed callbacks. Initialize browser-only integrations after mount and clean them up.
- Inspect dev console warnings as well as errors; production can omit hydration diagnostics. Fix mismatches at the cause. Do not hide them with a page-wide `ClientOnly`, `ssr: false`, blanket mismatch suppression, timeouts or forced remounts. Small truly browser-only widgets may use `ClientOnly` with an appropriately sized accessible fallback.
- Clean up listeners, observers, timers, object URLs and subscriptions; cancel obsolete requests when supported. Avoid deep watchers, render-time DOM measurements and reactive copies of derived data. Use computed state; bound retained caches and lists.
- Use Nuxt navigation/error APIs and locale-aware links; handle direct loads, back/forward and route reuse. **Same-page links scroll smoothly without changing URL/hash/history**; follow the guide's anchor rules. No global link interception/manual locale prefixes. Middleware does not authorize server requests.
- Use private runtime config on the server and `runtimeConfig.public` only for public values. Configure the layer's API URLs for deployment. Do not expose secrets, trust browser user/cart totals, cache personalized responses globally or forward credentials to arbitrary origins. Validate and authorize server actions.
- Preserve compatibility with both production SSR and static generation. Use existing route rules/deployment settings deliberately; plan dynamic routes/data and runtime API boundaries for both outputs. Do not enable experimental features, streaming or manual chunking merely because they exist.

## 9. Styling, accessibility and performance

- Use the existing Tailwind **v4** pipeline and scoped component CSS; do not install another Tailwind or add v3 configuration/CDN scripts. Do not reimport the layer's stylesheet in a consumer. Shared site tokens need a deliberately registered application stylesheet loaded in the intended order.
- Scope application selectors under a site root (or use SFC scoped CSS) from the start. Declare shared theme tokens at their intended owner and verify computed values on `html[data-theme]` and site surfaces in both themes. Consider selector specificity, source order and Tailwind cascade layers; do not accumulate conflicting utilities, broad resets or increasingly specific emergency overrides. Do not assume an unlayered base rule can safely override a layered utility.
- Use complete statically discoverable class strings, not `bg-${color}-600` or similar interpolation. For dynamic values use validated CSS variables. Class attribute order does not solve conflicting utilities; remove the conflict. The build strips `!important`: it is not an escape hatch.
- Start narrow, then recompose with verified breakpoints. Keep useful gutters at intermediate widths too. Do not hide overflow on the whole page to mask bugs, shrink the site with transforms or force text into fixed-height boxes. Use `min-width: 0`/wrapping where needed; test long translations, not only short English labels.
- Check the header at 320px with real branding, longest labels and theme control. Prevent unintended logo shrinking/wrapping; recompose navigation or use concise mobile labels with equivalent accessible names. Fix the sizing/inheritance cause before adding breakpoints or hiding essential actions.
- Keep semantic headings with one descriptive visible h1, logical sections, real labels, visible keyboard focus and accessible control names. Prefer existing accessible primitives; verify their rendered semantics. Do not recreate their focus/keyboard behavior. Target WCAG 2.2 AA, adequate contrast and approximately 44px touch targets where practical; support 200% zoom and keyboard-only use.
- Use `SafeNuxtImg`/`SafeNuxtPicture` and existing media components. Reserve dimensions/aspect ratio and supply correct responsive sizes/alt text. Inspect static-mode output: `SafeNuxtImg` falls back to a plain image and does not guarantee transformed variants there. Never put the hero in an intersection-lazy loader; prioritize only actual LCP candidates. Lazy-load noncritical media and defer heavy widgets.
- Use existing font/image optimization and consent-aware integrations. No speculative service worker, preload-everything strategy or extra optimization plugin. Measure before changing framework performance settings. Aim for LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at the 75th percentile; distinguish lab observations from real-user measurements.
- Use widely supported CSS for essential layout. Newer features need progressive enhancement appropriate to supported browsers, not blanket polyfills or custom fallback engines. Respect reduced motion; avoid gratuitous blur, repaint-heavy animations, `transition-all` and permanent `will-change`.

## 10. Layer conventions: i18n, SEO, consent

- Keep `multi18n` and `useMultiLang`; do not install a second i18n system. Default-locale URLs are unprefixed. Use literal `t`/`tn` keys or the documented safelist for dynamic keys so production tree shaking retains them. `useSafeList` is build/server-only; never import it into the client bundle.
- Shared interface strings belong in locale namespaces. For a complete reusable ready page, follow the README's ready-page contract: local typed content/appearance, complete locale defaults, `useReadyPage`, `PageReadyLocalized`, `mergeReadyContent` and `readyCssVariables`; do not recreate fallback/merging/SEO. Verify actual ready files exist before assuming a named page is available. Arrays in ready overrides are replaced, unlike the template's config array merge.
- Use `useAppSeo` (or ready-page SEO) and existing structured-data components; configure `myelophone.siteDomain`, localized metadata and real assets. Do not duplicate canonicals, hreflang, breadcrumbs/FAQ JSON-LD or invent schema facts. Keep private/error pages out of indexing; don't wrap ordinary SEO content in `SeoContentNoIndex`.
- Do not load analytics, marketing, maps, video embeds, forms or chat outside the documented consent flow. Reuse consent wrappers/presets and verify categories/CSP domains. Grid background support is not proof of consent compliance for an external provider. Keep consent UI mounted once.

## 11. Verification is a delivery requirement

- **Website delivery requires both `yarn build` and `yarn generate` to pass**, plus applicable type/lint/tests and browser checks of each output. Test generated files on a static server: SSR success does not prove SSG compatibility. Follow [dual-mode checks](docs/creative-direction/DESIGN.md#dual-mode-delivery). Documentation-only edits need no rebuild. `biome:check` writes fixes: keep changes scoped.
- For substantial website work, inspect the **rendered built site**, not just code or HTTP 200. Check 320, 390, 768, 1024 and 1440px widths, intermediate resizing, short landscape and 200% zoom. Inspect every distinct page template; capture and actually examine at least a narrow and a wide screenshot, including below-fold sections/footer.
- Review hierarchy, typography, spacing, crops, backgrounds and product identity. Fix the highest-impact defect and reinspect; generic/unfinished composition fails even when compiled. Include a separate refinement/removal pass and consistent action/result wording.
- Verify actual semantic tags/landmark counts and computed nested typography alongside screenshots. Inspect screenshots at a readable scale, not only a shrunken full-page image. After a theme change or navigation, scroll through below-fold content before judging reveal visibility; verify the newly mounted content becomes readable, rather than suppressing the effect to make a screenshot pass.
- Exercise actions, mobile navigation, keyboard/Escape, forms/async states, themes and console/asset/hydration errors. Test direct loads, client navigation, back/forward and sticky-header fragments. Verify reveals, reduced motion and no-JS content. Automated interactions must await hydration; keep CSP enabled and use function callbacks instead of eval-based test code.
- Review the diff for duplicated package behavior, manual auto-importable imports, raw substitutes for Grid components, generated files, fake content/controls, unnecessary dependencies and changes to user work.
- Report reused package capabilities, concrete changes, checks actually performed and remaining limitations. If browser/runtime tools are unavailable, complete available checks and explicitly mark visual/interaction acceptance unverified. Never equate build success or an automated score with a polished website.

## 12. Application ownership and commands

- This template builds production sites. Put pages in `app/pages/`, chrome in `app/layouts/`, compositions in `app/components/` and assets/locales/composables in their Nuxt 4 directories. Replace welcome/demo content and metadata. Do not develop the package inside the application.
- Keep `extends: ['@myelophone/nuxt']` and the config loader. Root `myelophone.ts` is project config; `myelophone.dev.ts` is a reference, not an automatic override. Loader objects merge recursively; arrays append/deduplicate primitives rather than replace. Configure actual locales, domain, SEO, API URLs and only needed integrations. Secrets stay private. Follow the README's goserver contract when applicable; never infer authentication from the UI.
- The local `docs/creative-direction/` owns design rules; installed package documentation owns technical APIs. Read only matched profiles through the local router. Do not move site instructions back into the layer or copy/shadow its source. If installed instructions are absent, inspect version-matched source/README, report the gap and continue independent work; never silently upgrade.
- Use pinned Yarn/Node requirements and the existing lockfile (`yarn install --immutable` when current). App `yarn dev/build/generate/preview/server` scripts target the application; inspect any playground/profile commands separately. On native PowerShell set the scripts' equivalent environment variables and run the local Nuxt CLI, preserving `NODE_OPTIONS` and `PROD_DIST=true`; use `NUXT_STATIC=true` only for generation. Never omit flags or leak static/playground mode into SSR checks.
- Both `yarn build` and `yarn generate` and their browser checks are required as described above. A checker failing before inspecting app files is blocked: report versions/error; no dependency patches, suppressed checks or silent upgrades. `biome:check` writes fixes; review scope.
- Preserve existing user changes, license/copyright notices and release metadata. Do not deploy/publish or change dependencies without task authorization. Use available relevant skills when helpful, never install/invent them from a name alone.
