# Navigation / header / contents / footer

Read only when these elements change. The inherited app shell already owns skip link, main, route announcement and global UI; do not duplicate them.

Choose navigation from real destinations and visitor tasks. Few marketing destinations may use a compact header; a true operational app may need persistent side navigation. Long editorial content may benefit from a quieter TOC. These are not reasons to add a mega-menu, sidebar or second fixed bar to every site.

Use installed responsive/horizontal menus, links and breadcrumb contracts when suitable. Keep brand, current location, useful primary action and theme control recognizable. A menu must open/close and support the package's actual keyboard/focus/Escape behavior. No raw copied navigation primitive or fake destinations.

On mobile prioritize compact real navigation, branding/theme control and essential action. Avoid shrinking the logo or hiding necessary routes just to keep desktop proportions. Reuse appropriate disclosure for secondary paths. Do not assume a small viewport means no keyboard or hover-capable device.

Coordinate sticky-header height, safe-area needs and overlays; focused controls/headings must remain reachable. Same-page actions use the shared smooth/no-hash/history/focus contract; other routes preserve normal links and modified clicks. No global interception or manual locale prefixes.

Footer contains useful real routes/contact/legal information when available, not invented pages. Do not copy a reference's announcement strip or add another global consent/scroll-top/search instance.

Verify longest supported labels at 320px and zoom, open/closed states, route reuse/back, theme persistence and release of sticky/overlay UI.
