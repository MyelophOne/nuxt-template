# Software / SaaS / developer-tool marketing

Read to explain/adopt/download a tool. Operational screens belong to APPLICATION.md only when those screens are in scope.

- **Workflow explains it:** concise proposition/action then an enlarged task-bearing product detail. Native UI may occupy a bounded stage; large raster hero imagery still follows the full-bleed rule.
- **Developer adoption:** verified quick-start/command, requirements and relevant evidence close to the action. Copy controls copy the right text and expose failure; viewing a sample never executes its commands.
- **Download:** confirmed asset/platform choice, requirements and alternative path, then useful proof. Never guess releases/URLs or change first-render markup from client platform detection.

Continue through distinct capabilities with real output, constraints/integrations, adoption/selection guidance and the actual next step. Plans/comparisons need confirmed data. No default counters, customer logos, charts or fake auth. A useful labeled static sample beats an inert fake interactive product.

Make the task-bearing detail legible, with coherent input, selected state, output and explanation. User-selected scenarios must actually update the example; no autoplay hero rotation or disguised carousel. Reserve size across states.

Mobile prioritizes proposition/action then readable proof. Crop a relevant detail instead of shrinking a desktop window into noise. Long commands may scroll locally, not break the page.

Inspect installed tabs/segmented controls, media and feedback APIs; don't add terminal/search/tab/animation engines. Preserve theme, i18n, consent and no-JS reading.

Verify understanding, evidence, requirements and the genuine adoption outcome in both outputs; no misleading progress/comparison/download result.
