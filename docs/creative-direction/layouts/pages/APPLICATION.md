# Application / dashboard / admin / settings

Read for repeated operational work, not public marketing. Preserve the product's established system; novelty must not make common tasks unpredictable.

| User's task | Starting layout |
| --- | --- |
| Monitor/diagnose | Current status and relevant exceptions lead, then interpretable detail/action |
| Process records | Search/filter toolbar → coherent list/table → item detail or real bulk actions |
| Edit/manage a resource | Resource identity and section navigation → grouped fields/content → save/result |
| Work across objects | List/detail or bounded workspace panels, evident active item and return path |

Use a sidebar only for justified repeated destinations. Make current location and primary operation evident; no floating component demo or arbitrary four-KPI dashboard. Charts and numbers need useful actual data. Density serves frequency/complexity, not a stock admin template.

A dominant work region gets quieter navigation/context. Related controls group tightly; different operations separate. Keep coherent surface/type/border/radius/spacing roles, with elevation for real overlays. No fixed opacity system, obligatory sidebar color or second token engine.

On mobile adapt panels/list/detail into a clear sequence while preserving operations, labels, state and focus. A real table may scroll locally with associated headers. Don't just hide critical columns/functions. Repeated tasks should respond promptly without long choreography.

Reuse actual menus, tabs, disclosures, forms, stores, API/data-fetching and inherited globals. No replacement router/theme/i18n/control shell. Marketing section quotas do not apply to operational/account screens.

Verify realistic empty/loading/error/permission states, long data, rapid repeat input, cancel/save/recovery and return navigation. Test actual request/state boundaries, keyboard/touch and both outputs; never fabricate successful operations.
